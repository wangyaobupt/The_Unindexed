为什么是 coding agent 先跑出了商业价值？

很多人很自然地把答案落在程序员身上。程序员工资高，软件行业数字化程度高，代码本身又是文本，刚好适合大模型生成，所以 coding agent 先起来，好像只是因为这块土壤最肥。这个解释太浅。它把 coding agent 理解成了程序员的提效工具，于是讨论很快会滑向另一个熟悉问题：程序员会不会被替代，初级程序员还有没有价值，资深程序员是不是可以一个人干三个人的活。

这些问题都成立，但它们没有击中更大的东西。coding agent 的真正商业价值，是 problem solving。写代码只是它现在最容易被看见、最容易被计量、也最容易被包装成产品的一层外壳。人从来不是为了 coding 而 coding，就像没有人为了打车而出门打车。打车是为了去办事、吃饭、见人、回家。coding 也是一样，它把现实世界里的某个问题压缩、抽象、建模成计算机可以执行的流程。真正值钱的从来不是那几行语法，而是这个转化动作。

我觉得，“Claude Code”或者“Codex”这样的名字，既准确，又画地为牢。准确，是因为它们确实从代码工作流里生长出来；画地为牢，是因为名字会把人的注意力锁在“写代码”上，让很多不写代码的人以为这件事和自己无关。最应该关心这类工具的人，可能并不是程序员，而是那些在各自行业里有真实问题、有解决思路、但过去没有能力把思路变成程序的人。

以前这个转化动作被很多专业分工把持着。一个业务人员想做一套内部工具，要先找产品经理讲需求；产品经理要理解以后写文档；架构师要判断怎么做；程序员要实现；数据分析师要处理数据；DBA 要管库；中间还要反复开会、对齐、改口径。复杂系统必须有分工，分工也制造了很高的最低启动成本。很多行业里的小问题、局部问题、长尾问题，并不是没有价值，而是不值得动用一整套专业分工。它们于是被留在 Excel、手工表格、临时脚本、口头经验和重复劳动里。

一个做投资研究的人，想把一批公告、财报、交易数据按自己的逻辑清洗出来，过去最现实的办法可能是手工整理，或者找会写脚本的人帮忙。一个做运营的人，想把每天散落在不同系统里的记录拼成一个异常提醒，过去可能只能忍受复制粘贴，或者等公司排期。一个小行业里的从业者，脑子里非常清楚自己要比较什么、筛掉什么、保留什么，但他不会写代码，于是他的想法只能停留在表格和经验里。被压住的是问题解决能力，只是它过去经常伪装成一个不够大的“软件需求”。

coding agent 改变的是这个门槛。它让一个不具备编程能力、但具备问题意识和逻辑思维的人，第一次有机会把自己的解决思路直接推向可执行状态。对专业程序员来说，从“自己写”到“带 AI 写”，是效率升级；对这类非专业用户来说，从“完全写不了”到“能做出来”，是能力跃迁。前者是速度变快，后者是世界变大。这两件事的性质不一样。

## 代码里沉淀的是问题解决史

> 代码的本质，不是程序，而是人类把现实问题变成流程的记录。

coding 为什么能成为第一个明显跑出来的 agent 场景？更深的原因在于，代码世界里沉淀了过去几十年人类把真实问题计算化的案例。

大约八十年来，计算机程序一直在进入真实世界。从早期的科学计算、军事计算，到银行业务系统、制造业管理系统、企业 ERP、互联网产品、移动应用、数据分析平台，coding 这把锤子几乎在每个行业都敲过钉子。每一次写程序，本质上都不只是把语法写对，而是把某个行业里的流程、规则、约束、异常和目标，翻译成机器可以执行的结构。

所以代码训练数据里最宝贵的东西，远不止 Python 语法、排序算法、设计模式，或者某个框架的最佳实践。更宝贵的是大量“现实问题如何被建模”的案例研究。一个库存系统如何理解入库、出库、盘点、损耗；一个交易系统如何处理订单、撤单、成交、风控；一个报表系统如何把业务口径变成 SQL；一个自动化脚本如何把原来需要人工操作十分钟的步骤压成一次命令。这些东西看起来是代码，其实是人类把现实世界压成计算流程的历史痕迹。

LLM 在消化代码时，也在消化这些痕迹。无论它是在模式匹配，还是在更深层的表示空间里形成了某种联系，外部观察者看到的结果已经足够明确：今天的 coding agent 不只是会补全函数，它开始具备把一个明确问题拆开、建模、实现、验证的能力。它读到的常常已经不是“请帮我写一个 for 循环”，而是“我现在有一批数据，想按这个标准筛出异常，再生成一个能反复运行的流程”。这已经不是狭义的写代码。

## 真正的受益者

如果把人粗略分成几类，coding agent 带来的收益其实并不平均。

第一类人，不能定义问题，没有解决思路，也不会写代码。工具再强，对他们的改变仍然有限。AI 可以替人执行，也可以帮人补全很多细节，但它不能稳定地替一个人生成真实需求。一个人如果只会说“帮我做个有用的东西”，最后多半只会得到一个看起来体面的空壳。绝大多数人并不会因为出现了 coding agent，就突然获得构造问题的能力。

第二类人，有问题，有思路，但不会写代码。这类人才是最大的受益者。他们可能是投资者、医生、教师、律师、供应链从业者、内容创作者、小企业主，也可能是任何一个长期待在具体业务现场的人。他们不一定懂软件工程，但他们知道什么东西麻烦，什么口径经常错，什么数据每天都要重复处理，什么判断如果能自动化会节省大量时间。他们过去缺的不是想法，而是把想法变成工具的能力。coding agent 给他们补上的，正是这一段。

这类人通常只是每个行业里的少数人，是各行各业里那一小部分对效率、结构和结果更敏感的人。工具的普及不会让第一类人成为第二类，但会极大改变第二类人的上限。过去他们的想法必须等别人排期，今天他们可以自己把第一版跑起来；过去一个小工具不值得雇人做，今天它可能只需要几轮对话和一点耐心；过去一个行业知识只能停留在个人经验里，今天它可以被固化成一个可复用流程。

第三类人，是不参与建模、但会写代码的执行层程序员。他们会提效，也会承压。短期内，AI 会让他们完成更多任务，减少很多机械劳动；长期看，如果他们始终不进入问题定义和系统判断，就会越来越像一个中间环节。中间环节只要成本足够高、接口足够明确，就一定会被压缩。

在“问题明确 + 复杂度中等”的区域里，很多执行层程序员未必天然比 coding agent 强。因为相当多的执行层程序员习惯拿着产品设计文档写代码，业务问题已经被别人拆完了，边界已经被别人定完了，他负责的是实现。实现能力不自动包含完整的问题建模能力。当一个 agent 可以听懂业务描述、追问缺口、提出方案、写出程序、再根据反馈修改时，它覆盖的已经不是“程序员打字”这件事，而是产品经理、数据分析师、初级程序员之间那段漫长的转化链条。

这才是程序员真正危险的地方。危险不在于“AI 会写代码”，而在于如果一个程序员只会写别人已经建模好的代码，他的专业位置会被压缩成一段可替代资源。过去他是必要角色，因为非技术人员无法跨过代码门槛；现在门槛下降以后，必要性就要重新证明。未来程序员最稳的位置，不来自更熟的语法或者更多的框架，而来自他能不能参与问题定义，能不能理解业务约束，能不能在系统变复杂时保住结构和可维护性。会写代码仍然重要，但只会写代码不再足够。


第四类人，是会建模、也会写代码的资深程序员、架构师。他们会受益，但这种受益更像杠杆变长，还没到范式跃迁。coding agent 让“一个人干三个人、乃至十个人的活”越来越现实，但还没有让“一个人指挥一百个人”稳定成立。两者之间的差距不在代码，而在认知的可扩展性。一个人可以并行启动很多 agent，但他能否同时理解它们的产出、发现结构性错误、判断取舍、承担后果，是另一回事。AI 放大的是人的工作半径，不自动放大人的判断半径。

所以，把 coding agent 理解成程序员提效工具，会低估它对非程序员的意义；把它理解成可以自动替代专业人员，又会高估它对多数人的意义。它真正打开的空间，是那些原本“有问题、有思路、但不值得进入软件工业流程”的地方。那里过去长期被成本压住，现在开始变得可解。


## “计算”正在变成通用能力

这件事的本质，是“计算”正在从专业能力变成通用能力。

从 90 年代到现在，很多行业人面对已经数字化的世界时，真正的门槛不是有没有想法，而是能不能调用计算机完成复杂任务。这个能力长期被垄断在程序员、数据分析师、软件供应商和企业 IT 部门手里。普通行业用户即使有想法，也只能在这些专业角色允许的范围内表达需求。

现在，接口开始变了。自然语言、文件、数据、代码、命令行、浏览器、数据库之间的距离在缩短。一个人只要能清楚描述问题，能判断结果，能承受试错，就开始拥有某种初级计算能力。这里的关键仍然是“清楚描述问题”和“判断结果”。coding agent 不会让绝大多数人突然变成创造者，也不会把没有需求的人变成有需求的人。它更像一种放大器：谁本来就对问题敏感，谁就会被放大；谁本来就只是在等别人告诉自己要做什么，谁得到的变化就有限。技术降低的是执行门槛，不是思考门槛。甚至因为执行门槛下降，思考门槛会变得更加显眼。

所以，coding agent 最值得看的地方，是它把“能解决问题的人”和“能写代码的人”之间的绑定关系拆开了。过去这两种能力经常必须合在一个人身上，或者通过组织分工勉强拼起来。现在，真正的中心开始回到问题本身：你能不能定义它，能不能拆开它，能不能给出解决思路，能不能判断机器给出的结果是否真的解决了它。

如果说今天这类工具还有什么明显障碍，那就是它们仍然带着太强的程序员气味。CLI、Bash、repository、commit、build，这些词对程序员来说很自然，对大多数行业用户来说就是门。很多人一听“写代码”三个字就已经离开了。即使界面变成 GUI，即使入口越来越友好，只要它仍然用“build something”这样的语言召唤用户，它吸引到的也主要是已经把自己想象成建造者的人。

真正需要被释放的长尾需求，很多时候并不会以“我要 build 一个软件”的形式出现。它更可能是“我每周都要整理这张表，能不能别再手工弄了”；“我想把这些公告按我的标准筛一遍”；“我想每天自动检查这些指标有没有异常”；“我想把几个系统里的记录对上，看看哪里漏了”。这些人要的是 problem-solving experience。工具如果一直要求他们先接受程序员语言，很多需求还没开始就已经被挡住。

## 商业价值在长尾问题里

真正的生产力进步，往往不是让原来已经值得被解决的大问题更华丽地解决一次，而是让大量原本不值得被解决的小问题第一次变得可解。一个大公司可以雇团队做系统，一个大项目可以拉预算、立项、排期。最长期被压抑的，是那些太小、太散、太具体、太依赖个人理解的问题。它们单个看不够宏大，合在一起却构成了大量真实劳动的摩擦。

阿波罗登月计划本身在商业上没有直接收益，但它留下来的技术、材料、工程方法和产业能力，后来在商业世界里持续外溢。AI 也可能经历类似的路径。那些替代人类解决终极问题的宏大叙事会继续存在，解决疾病、自动驾驶、管理组织，这些方向也会继续吸收资源；但 AI 的第一性商业价值，未必在这些星辰大海里，而在把原来需要专业分工才能启动的计算能力，释放给那些站在具体问题旁边的人。让一个教师能自己做出适合班级的分析工具，让一个小企业主能自己搭起库存提醒，让一个研究者能把反复处理的数据流程固化下来，让一个投资者能把自己的筛选逻辑变成每天自动运行的程序。每个例子都不宏大，但这才是生产力扩散的真实形态。

这才是 coding agent 的商业价值：让原本不值得被解决的问题变得可解。**这不是“AI提升效率”，而是改变了哪些问题值得被解决的边界**
